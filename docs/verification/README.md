# Verification capability status

The deterministic verification engine is **available**. It is built around a versioned verification case that freezes input, reference or enrichment data, expected output, comparison rules, and lineage or checkpoint evidence. It runs the candidate against those frozen facts, reconciles actual and expected output deterministically, and reports an earliest confirmed divergence or an honest unknown interval. Both shipped examples drive that engine end to end on frozen synthetic material.

The portable case contract now has mechanically generated, inspectable [JSON Schema](schemas/verification-domain.schema.json) and [serialization projection](schemas/verification-serialization.json). Their source is the versioned Python domain contract; the generation check refuses stale projections. The central validator rejects unknown schema versions and fields, unresolved or cyclic lineage, missing frozen roles or outcomes, ambiguous grain, unscoped policy declarations, assurance declarations whose identity facts are incomplete or whose declared level contradicts the evidence they cite, and datasets whose declared provenance and generator record contradict each other. An evidence gap is not a refusal: a run whose evidence cannot support a complete outcome is recorded as an insufficient-evidence result and reported with what remains unknown. Once a case policy is observed, changing it requires a new case rather than silently altering a run.

Beside the engine, delivery teams use the supplied verification-record template to declare evidence, negative cases, reviewer outcomes and named acceptance for an engagement. Those records and the synthetic examples rest on synthetic material, and neither is a live-system certificate.

Synthetic inputs, reference data and expected outputs are a first-class fill for a case that real data has not reached. The portable case contract carries that label: every frozen dataset declares its provenance, a synthetic one carries the generator, seed, constraints and the identities of the datasets that constrained it, every expected output declares its provenance and may declare a synthetic derivation as its origin, and a case reports whether its evidence reads as real, mixed or synthetic. Results and the acceptance record carry the same label, so a synthetic pass reads as labelled progress rather than parity with real data. The product [README](../../README.md) states which classes of finding fail closed and which are only labelled; it is the single textual source for that rule.

The two environment contracts now ship with an adapter kit. It carries reference adapters that answer each contract from values held in memory or from material laid out in a directory the adopting environment names, the declaration an adapter uses to state what it can do and what its answers are worth, and a conformance suite that reads an adapter's answers against its claims. The suite refuses a capability the port never showed, an assurance above the plainest level with no input named to rest it on, a port contract version these ports do not declare, a value of the wrong shape, and any value or refusal carrying a machine route or a written credential. It never recomputes a digest: a declared digest is read for its form there and checked for its truth by the intake workflow. The [environment-adapter contract](environment-adapters.md) states what an adapter implements, what it may declare, what stays in the adopting environment, and how a failure reads.

Portable records retain identifiers, cryptographic fingerprints, counts and approved summaries only. Raw data, credentials, private values, machine paths, signing, retention and certification remain environment-owned. Any diagnostic advice is a human-controlled proposal: it cannot alter a case, evidence, tolerance, candidate, work graph or acceptance outcome. See the reader-facing [capability status guide](../product/capability-status.md) for what each status term means and which claims the adopting environment owns.
